# Evaluation: does the graph evidence matter?

Generated by `python -m eval.baseline` on the synthetic fixture scenarios (`graph/fixtures/scenarios/`).
Each ranker sees the same injected incident. For S5 (two simultaneous faults) the top two must be the two causes.

| Scenario | Expected | Coverage only | Coverage + hops | rootgraph scorecard |
|---|---|---|---|---|
| S1 Security-group rule revoked | `sg-db` | ✗ `i-host1` | ✗ `i-host1` | ✓ `sg-db` |
| S2 Shared host saturated | `i-host2` | ✓ `i-host2` | ✓ `i-host2` | ✓ `i-host2` |
| S3 Plain service failure | `svc:payments` | ✓ `svc:payments` | ✓ `svc:payments` | ✓ `svc:payments` |
| S4 Repeat of S1 (memory) | `sg-db` | ✗ `i-host1` | ✗ `i-host1` | ✓ `sg-db` |
| S5 Two faults at once | `sg-db`, `svc:payments` | ✗ `i-host1`, `svc:payments` | ✗ `i-host1`, `sg-db` | ✓ `sg-db`, `svc:payments` |
| **Correct** | | **2/5** | **2/5** | **5/5** |

What the columns mean:

- **Coverage only** is the first row of Q2 (`correlate_alerts`): the node that explains the most alerting nodes.
- **Coverage + hops** re-scores the same candidates with only the topology terms of the scorecard (no probes, paths, changes or memory).
- **rootgraph scorecard** adds probe health, broken network paths (Q4/Q10), recent changes (Q5) and incident memory (Q7).

Why coverage alone fails: in S1 and S4 the security-group rule is not on any dependency chain, so a pure upward walk can't reach it and blames host-1, which explains every alert but is healthy. In S5 it finds payments but misses `sg-db`. Only the path check (Q4 + Q10) surfaces `sg-db`, and only the probes clear host-1. Coverage is enough when the cause sits on the dependency chain itself (S2 shared host, S3 stopped service).

Limits: five hand-made scenarios on a 17-node estate; the weights were tuned on them (see README, Limitations). This shows the mechanism, not general accuracy.
